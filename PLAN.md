# План развития HarbourDBF.NET

Цель — проверить и доработать библиотеку для корректной работы с DBF/FPT/CDX на стенде `read-dbf`, включая совместную работу с Harbour. Сначала выполняем и проверяем x86; x64 рассматриваем после завершения x86.

1. Открыть все шесть синтетических CDX и проверить чтение, поиск и изменение данных независимой проверкой Harbour без перестроения индексов.
2. Последовательно покрыть и исправить типы, поиск, запись и сопровождение индексов; проверить управление сессиями, ошибками и ресурсами.
3. Проверить блокировки и конкурентную работу отдельных процессов, а при необходимости — SMB и особенности CRM на согласованной копии данных. Реальные рабочие файлы не изменять.
4. Зафиксировать результаты и ограничения, затем проверить производительность и отдельно выполнить этап x64.

Для каждого дефекта сохранять воспроизводимую проверку, а завершённые изменения оформлять отдельными коммитами. Подробные сценарии и эталон Harbour находятся в соседнем проекте `read-dbf`.

Проверка согласованной копии CRM и этап x64 отложены пользователем; текущие результаты относятся к синтетическим данным x86.

## Доступ к Harbour VM и массовые операции

После завершения текущей задачи по типизированному API реализовать единый внутренний поток-исполнитель для Harbour VM. Вызывающий код сможет обращаться к API с разных потоков; операции Harbour выполняются последовательно. До внедрения проверить и при необходимости изменить инициализацию и завершение VM, чтобы они соответствовали выбранной модели потока, а также определить безопасное завершение исполнителя, обработку ошибок и повторного входа.

Очередь исполнителя ограничить: по умолчанию 256 ожидающих операций, с возможностью задать другую ёмкость при настройке. Асинхронный вызов при заполненной очереди ожидает свободного места с поддержкой отмены ожидания. Для синхронного вызова определить безопасное ожидание, не допуская взаимной блокировки при повторном вызове с потока исполнителя. Не добавлять пока автоматический подбор размера или дополнительные политики очереди. Ограничение очереди не ограничивает количество задач, заранее созданных вызывающим кодом.

Позже отдельно спроектировать и реализовать механизм Bulk-операций для массовой обработки: ограниченные пакеты и сокращение накладных расходов переходов через мост. Границы пакетов и API определить после измерений; не включать Bulk в реализацию очереди.

## Состояние таблицы после частичного сбоя записи

Отдельно определить и реализовать политику для открытого экземпляра таблицы после ошибки уже начатой записи или освобождения блокировки. Например, `Update` может успеть записать имя, затем получить ошибку при записи кода или `Commit`: отката нет, и запись с индексами может оказаться частично изменённой. Если ошибка возникла при освобождении блокировки, также может быть неизвестно, удерживается ли она ещё.

Рассмотреть два варианта: запретить обычные операции через этот экземпляр до его закрытия и повторного открытия либо оставить доступ и возложить проверку состояния и восстановление на вызывающий код. Закрытие и повторное открытие сами по себе не откатывают частичную запись. Отличать эти случаи от ошибки callback или проверки входных данных до записи и от неудачной попытки получить блокировку. Определить сохранение основной ошибки вместе с ошибкой освобождения, диагностическую информацию и поведение остальных таблиц сеанса; добавить воспроизводимые проверки частичных сбоев. Пока типизированный API не запрещает дальнейшее использование экземпляра автоматически.

## Точная запись больших целых

Отдельно разработать и проверить транспорт записи полного диапазона `long`. На текущем стенде передача `long.MaxValue` через JSON/Harbour не сохранила точное значение; типизированная запись в `N` поэтому отклоняет числа с модулем от 2⁵³ и выше до изменения файла. Проверить положительные и отрицательные границы, чтение после повторного открытия и результат независимым Harbour. До выполнения этого этапа не расширять заявленный диапазон записи.
