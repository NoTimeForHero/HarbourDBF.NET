# Лёгкие проверки и данные

Тесты используют файлы из `tests/fixtures`, созданные специально для этого репозитория. В каждом DBF по три синтетические записи; реальных данных здесь нет.

| Файл | Содержимое |
| --- | --- |
| `basic.dbf`, `basic.fpt` | `ID` (`N`), `NAME` (`C`), `BIRTH` (`D`), `ACTIVE` (`L`), `AMOUNT` (`N`), `NOTE` (`M`). У первой записи memo `First memo`. |
| `basic_id.cdx`, `basic_name.cdx` | Отдельные CDX, теги `ID` и `NAME`. |
| `special.dbf` | `IDZ` (`+`), `TSZ` (`=`), `VMZ` (`^`), `STAMP` (`@`) и `NAME` (`C`). В `STAMP` заданы фиксированные значения с миллисекундами. `TSZ` создаётся Harbour по часам машины. |
| `special_id.cdx`, `special_time.cdx` | Отдельные CDX, теги `IDZ` и `STAMP`. |

Запуск приведён в [README](../README.md). `LightTests` копирует готовые файлы из каталога сборки в новый временный каталог, выполняет примеры и удаляет временную копию. Он проверяет число записей каждого исходного DBF, изменение/добавление, удаление и восстановление, чтение FPT, пустые дату и timestamp, поиск по отдельным CDX, значения служебных полей и сопровождение индексов после повторного открытия. После работы сверяются хеши файлов, из которых создавалась копия.

Исходный код проверок — [tests/Program.cs](../tests/Program.cs). Он рассчитан на наглядность и быстрый локальный запуск, а не на полное испытание корректности. Более широкие сравнения с независимым Harbour, включая конкурентные процессы и специальные индексы, находятся в соседнем проекте `read-dbf` и не нужны для запуска этих примеров.

Типизированные сценарии дополнительно проверяют чтение и поиск, видимость удалённых записей, добавление, обновление и повторное открытие индексов. Отдельный дочерний x86-процесс удерживает блокировку записи, чтобы проверить отказ `Update` и `MarkDeleted` до вызова callback. Это проверка файловой блокировки; она не заменяет независимую проверку формата другим экземпляром Harbour или более широкие конкурентные испытания.

Отдельный дочерний процесс проверяет, что загрузка DLL не запускает VM, а её инициализация и завершение происходят на потоке исполнителя. Проверяются ограниченная очередь, отмена ожидания, завершение с принятыми задачами, ошибки и отказ повторной постановки с потока исполнителя. Типизированные операции также вызываются параллельно из нескольких потоков на разных открытых областях.

Для дополнительной проверки типизированной записи независимым Harbour соберите `verify-typed.prg` и передайте путь к нему через переменную окружения перед запуском LightTests. Программа только читает созданные тестом временные копии и открывает существующие CDX без перестроения. Из корня репозитория:

```powershell
$env:PATH = 'C:\borland\bcc58\bin;C:\MiniGUI_2607\harbour\bin;' + $env:PATH
& 'C:\MiniGUI_2607\harbour\bin\hbmk2.exe' 'tests/verify-typed.prg' '-comp=bcc' '-otests/bin/verify-typed'
if ($LASTEXITCODE -ne 0) { throw 'Harbour verifier build failed' }
$env:HARBOUR_TYPED_VERIFIER = (Resolve-Path 'tests/bin/verify-typed.exe').Path
try { ./tests/bin/Debug/net472/LightTests.exe; if ($LASTEXITCODE -ne 0) { throw 'Tests failed' } }
finally { Remove-Item Env:HARBOUR_TYPED_VERIFIER }
```

Без переменной обычный запуск LightTests не требует этого проверяющего приложения. Проверка не охватывает все типы индексов и все виды конкурентной записи.

Для разработки составных ключей [complex-fixture.prg](../tests/complex-fixture.prg) создаёт новую синтетическую DBF и многотеговую CDX в пустом указанном каталоге, затем повторно открывает их и проверяет поиск Harbour без перестроения. В проверенной сборке попытка создать тег `UPPER(ALLTRIM(NAME))` на этой схеме завершилась `Data width error`; вариант `UPPER(PADR(ALLTRIM(NAME),20))` с фиксированной шириной создаётся и ищется. Это наблюдение для конкретного стенда, а не утверждение обо всех версиях RDD.

## Пересоздание данных разработчиком

Готовые DBF/FPT/CDX уже находятся в Git; пересоздавать их для обычного запуска не требуется. Если нужно изменить набор, используйте [generate-fixtures.prg](../tests/generate-fixtures.prg) с Harbour 3.2 и BCC. Скрипт создаёт файлы только с известными именами и отказывается перезаписывать существующие. Из корня репозитория:

```powershell
$env:PATH = 'C:\borland\bcc58\bin;C:\MiniGUI_2607\harbour\bin;' + $env:PATH
New-Item -ItemType Directory -Force tests/bin | Out-Null
New-Item -ItemType Directory -Path tests/new-fixtures | Out-Null
Push-Location tests
try {
    hbmk2 generate-fixtures.prg -comp=bcc -obin/generate-fixtures
    if ($LASTEXITCODE -ne 0) { throw 'Generator build failed' }
    ./bin/generate-fixtures.exe ./new-fixtures
    if ($LASTEXITCODE -ne 0) { throw 'Fixture generation failed' }
} finally { Pop-Location }
```

Проверьте созданные файлы и только затем заменяйте версионируемый набор. Из-за автоматического времени `TSZ` и дат в заголовках двоичные файлы при повторном создании не обязаны совпадать побайтно. После изменения набора необходимо заново выполнить все лёгкие проверки и сравнить ожидаемые значения в коде.
