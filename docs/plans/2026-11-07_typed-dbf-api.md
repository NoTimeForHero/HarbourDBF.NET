# План типизированного API HarbourDBF.NET

Дата: 2026-11-07. Статус: реализация ограниченной первой версии начата.

**Обновление:** реализуется ограниченная версия с простыми индексами и записью; доступ к VM переведён на единый внутренний исполнитель. Фактически доступный API и ограничения описаны в [руководстве](../typed-api.md); остальная часть документа сохраняет целевой проект и открытые вопросы, а не описание реализованных возможностей.

## 1. Цель и границы

Спроектировать небольшой C# API поверх Harbour RDD, который убирает из прикладного кода управление алиасами, переключение рабочих областей, ручное форматирование ключей и обычные операции с блокировками. Модель остаётся обычным C#-классом, а имена DBF-полей, файлов индексов и тегов находятся в отдельном mapping.

Этот документ фиксирует предлагаемый синтаксис, контракты, ограничения и вопросы для следующего обсуждения. Все новые типы и методы в примерах являются проектируемыми. Примеры не компилируются с текущей библиотекой и не подтверждают поддержку показанных выражений индексами текущего стенда.

В текущую задачу не входят реализация библиотеки, изменение native DLL, добавление тестовых DBF/CDX, изменение формата существующих данных и модернизация целевой платформы. SQL, полный LINQ-провайдер, автоматическое отслеживание объектов, миграции и транзакционный движок не планируются как часть первой версии API.

Существенные уточнения к обсуждённым примерам:

1. `OpenTable` должен подключать все объявленные индексные файлы до первой записи. Вызов `cities.Index(mapping.ByCode)` только получает типизированное представление уже подключённого тега. Ленивое открытие только использованного поискового индекса недопустимо для режима записи.
2. Mapping обязан описать полный известный набор сопровождаемых индексных файлов, в том числе не используемых для поиска из C#. Отсутствие неизвестных внешних CDX нельзя доказать одним просмотром каталога или схемы DBF; вопрос полноты остаётся частью контракта конфигурации.
3. Кодовая страница Harbour и кодировка обмена с DLL задаются отдельно. В цельном примере обе настройки указаны явно: `UA866` и CP866. Это пример проверенной пары, а не выбор по умолчанию для любой таблицы.
4. Типизированное чтение дат и чисел требует отдельного преобразования по схеме. Текущий `GetValues` не возвращает готовые `DateTime` и не гарантирует требуемый числовой тип модели.
5. `Commit` не является транзакцией. Обёртка не должна обещать атомарную запись нескольких полей или откат при native-ошибке.
6. Многотеговые CDX, составные ключи, произвольные выражения, `UNIQUE`/`FOR`, префиксы и границы диапазонов требуют дополнительных независимых проверок. Текущие лёгкие примеры подтверждают более узкие сценарии с отдельными CDX.

## 3. Объектная модель

| Тип | Назначение |
| --- | --- |
| `DbfSession` | Владеет открытыми таблицами и ресурсами перечисления; задаёт область времени жизни работы. Не обещает отдельную Harbour VM или изоляцию глобальных настроек. |
| `DbfMapping<T>` | Неизменяемое после построения описание полей, преобразований и индексов. Не содержит открытых алиасов. |
| `DbfTable<T>` | Открытая таблица; чтение, добавление, изменение, удаление и получение индексов. |
| `DbfIndexMapping<T, TKey>` | Описание файла, тега и правил ключа. Принадлежит конкретному mapping. |
| `DbfIndex<T, TKey>` | Индексный доступ в рамках открытой таблицы, без публичного текущего указателя. |
| `DbfRecord<T>` | Самостоятельные материализованные данные и метаданные прочитанной записи. |
| `DbfRecordRef<T>` | Непрозрачная ссылка для обращения к физической записи конкретного открытого экземпляра таблицы. |
| `DbfIndexPrefix<T, TKey>` | Описание ограниченного обхода по последовательным ведущим частям ключа. |

`DbfRecord<T>` содержит `Value`, `Reference`, `RecordNumber`, `IsDeleted`. `Value` — обычный изменяемый объект без автоматического сохранения. Новое чтение создаёт новый объект; дальнейший поиск не меняет старый результат.

`Reference` не является бизнес-ключом, постоянной идентичностью строки или гарантией неизменности её содержимого. После закрытия таблицы использовать её для операций нельзя; повторное открытие создаёт другую область владения. Физический номер может измениться после `PACK` или замены файла. Политика таких внешних изменений требует отдельного решения.

## 4. Цельный пример API

Имена тегов, схема `City` и ширина частей составного ключа условные. Многотеговый `city.cdx` показан как целевой сценарий, который ещё нужно проверить. Пример не относится к файлам `tests/fixtures` и не предназначен для запуска на рабочих данных.

```csharp
using System;
using System.Linq;
using System.Text;
using HarbourDBF.NET;

public sealed class City
{
    public int Code { get; set; }
    public string Name { get; set; }
    public int ViewId { get; set; }
}

public sealed record CityNameKey(int ViewId, string Name);

public sealed class CityMapping : DbfMapping<City>
{
    public DbfIndexMapping<City, int> ByCode { get; }
    public DbfIndexMapping<City, string> ByName { get; }
    public DbfIndexMapping<City, CityNameKey> ByViewAndName { get; }

    public CityMapping()
    {
        Field(c => c.Code, "KCITY");
        Field(c => c.Name, "CITY").TrimEnd();
        Field(c => c.ViewId, "KVIEW");

        // KCITY
        ByCode = Index(
            key: c => c.Code,
            file: "city.cdx",
            tag: "BY_CODE");

        // UPPER(ALLTRIM(CITY))
        ByName = Index(
            key: c => c.Name,
            file: "city.cdx",
            tag: "BY_NAME",
            format: DbfKeyFormat.AllTrim().Upper());

        // STR(KVIEW, 4, 0) + UPPER(PADR(CITY, 30))
        ByViewAndName = CompositeIndex<CityNameKey>(
                file: "city.cdx",
                tag: "BY_VIEW_NAME")
            .Part(
                key: k => k.ViewId,
                field: c => c.ViewId,
                format: DbfKeyFormat.Str(width: 4, decimals: 0))
            .Part(
                key: k => k.Name,
                field: c => c.Name,
                format: DbfKeyFormat.PadRight(30).Upper());
    }
}

public static class Example
{
    public static void Run()
    {
        var mapping = new CityMapping();

        // Для примера — каталог подготовленной копии данных.
        using var db = DbfSession.Open(@"D:\SampleData");

        // DbfTable<City>; все объявленные CDX подключаются здесь.
        var cities = db.OpenTable(
            "city.dbf",
            mapping,
            mode: DbfOpenMode.SharedReadWrite,
            codepage: "UA866",
            encoding: Encoding.GetEncoding(866));

        // Получение представлений тегов не открывает файлы заново.
        var byCode = cities.Index(mapping.ByCode);
        var byName = cities.Index(mapping.ByName);
        var byViewAndName = cities.Index(mapping.ByViewAndName);

        // Поиск по обычному индексу.
        var found = byCode.FindFirst(4);
        if (found != null)
        {
            Console.WriteLine(found.Value.Code);
            Console.WriteLine(found.Value.Name);
            Console.WriteLine(found.RecordNumber);
        }

        // Поиск по выражению: нормализацию выполняет mapping.
        var named = byName.FindFirst("  Кострома  ");
        if (named != null)
            Console.WriteLine(named.Value.Name);

        // Составной ключ без склейки и форматирования строк.
        var key = new CityNameKey(ViewId: 1, Name: "Кострома");
        var exact = byViewAndName.FindFirst(key);
        if (exact != null)
            Console.WriteLine(exact.Value.Code);

        foreach (var record in byViewAndName.EqualTo(key))
            Console.WriteLine(record.Value.Name);

        // Равенство полной первой части составного ключа.
        var view1 = byViewAndName.Prefix(k => k.ViewId, 1);
        foreach (var record in view1.Scan())
            Console.WriteLine(record.Value.Name);

        // Первая часть равна 1, следующая начинается с "Кос".
        foreach (var record in view1.StartingWith(k => k.Name, "Кос"))
            Console.WriteLine(record.Value.Name);

        // Диапазон полных ключей с явно заданными границами.
        foreach (var record in byViewAndName.Range(
            from: new CityNameKey(1, "А"),
            to: new CityNameKey(1, "М"),
            bounds: DbfRangeBounds.IncludeBoth))
        {
            Console.WriteLine(record.Value.Name);
        }

        // Чтение по физическому номеру, начиная с 1.
        var physical = cities.ReadAt(recordNumber: 42);
        if (physical != null)
            Console.WriteLine(physical.Value.Name);

        // Новое чтение записи через её ссылку.
        if (found != null)
        {
            var fresh = cities.Read(found.Reference);
            if (fresh != null)
                Console.WriteLine(fresh.Value.Name);
        }

        // Полный обход; Where и Select выполняются в C#.
        var names = cities.Scan()
            .Where(record => record.Value.ViewId == 1)
            .Select(record => record.Value.Name)
            .ToList();

        // Добавление без автоматического upsert или проверки уникальности.
        var added = cities.Insert(new City
        {
            Code = 8,
            Name = "Кострома",
            ViewId = 1
        });
        Console.WriteLine(added.RecordNumber);

        // Callback получает свежие данные под блокировкой.
        var updated = cities.Update(added.Reference, city =>
        {
            city.Name = "Кострома — областной центр";
            city.ViewId = 2;
        });
        Console.WriteLine(updated.Value.Name);

        // Вычисление нового значения из актуального содержимого.
        cities.Update(updated.Reference, city =>
        {
            city.Name = city.Name.Replace(" — областной центр", "");
        });

        // Обе операции сами управляют блокировкой и фиксацией.
        cities.MarkDeleted(added.Reference);
        cities.Recall(added.Reference);
    }
}
```

Один `using` завершает работу со всеми таблицами. При необходимости таблицу можно освободить досрочно через `Dispose`; владение сеанса остаётся страховкой от пропущенного освобождения.

`record` в объявлении ключа — удобная форма примера, а не требование к модели пользователя. Возможность использовать обычный класс или структуру и минимальную версию C# нужно закрепить отдельно, сохранив текущую целевую платформу.

### 4.1. Таблицы во вложенных каталогах

Один сеанс может открывать таблицы из разных вложенных каталогов. Корень сеанса — базовый каталог для путей, а не требование хранить все DBF рядом.

В следующем примере все названия моделей, каталогов и файлов условные. Таблица покупателей находится в `catalog\customers.dbf`, а таблица заказов — в `sales\orders.dbf`. `CustomerMapping`, `OrderMapping`, свойство `Id` и индексы `ById`/`ByCustomerId` иллюстрируют проектируемый API чтения; их описание должно соответствовать схеме используемых данных.

```csharp
var customerMapping = new CustomerMapping();
var orderMapping = new OrderMapping();

using var db = DbfSession.Open(@"D:\SampleData");

var customers = db.OpenTable(
    @"catalog\customers.dbf",
    customerMapping,
    mode: DbfOpenMode.SharedReadOnly);

var orders = db.OpenTable(
    @"sales\orders.dbf",
    orderMapping,
    mode: DbfOpenMode.SharedReadOnly);

// Обе таблицы открыты; переключение алиасов скрыто внутри API.
var customer = customers.Index(customerMapping.ById).FindFirst(123);

if (customer != null)
{
    foreach (var order in orders.Index(orderMapping.ByCustomerId)
        .EqualTo(customer.Value.Id))
    {
        Console.WriteLine(order.RecordNumber);
    }
}

// Можно снова обратиться к первой таблице без SelectArea.
var anotherCustomer = customers.Index(customerMapping.ById).FindFirst(456);
```

Если таблицы нужны строго по очереди, раннее освобождение задаётся обычными областями `using` в том же сеансе:

```csharp
using (var customers = db.OpenTable(@"catalog\customers.dbf", customerMapping))
{
    var record = customers.Index(customerMapping.ById).FindFirst(123);
    // Работа с покупателями; режим по умолчанию SharedReadOnly.
}

using (var orders = db.OpenTable(@"sales\orders.dbf", orderMapping))
{
    var records = orders.Index(orderMapping.ByCustomerId).EqualTo(123);
    foreach (var record in records)
        Console.WriteLine(record.RecordNumber);
}
```

Второй фрагмент — альтернативный порядок открытия с теми же переменными сеанса и mapping, а не продолжение первого с повторным открытием уже открытых таблиц. Перечисления завершаются до выхода из соответствующего `using`; оставшиеся таблицы сеанс закрывает сам.

## 5. Контракты mapping и открытия

| Операция | Предлагаемый контракт |
| --- | --- |
| `Field(property, name)` | Связывает свойство с существующим полем. Проверяет совместимость с DBF-схемой при открытии. Не создаёт и не меняет схему. |
| `.TrimEnd()` | Преобразование при чтении конкретного свойства. Не влияет на формат ключа индекса и не даёт повода переписывать неизменённое поле. Без явной настройки строка сохраняет пробелы. |
| `Index(...)` в mapping | Объявляет тег, тип ключа и преобразование ключа. Файл и тег идентифицируются раздельно, порядковые номера тегов не становятся частью прикладного контракта. |
| `CompositeIndex<TKey>().Part(...)` | Описывает упорядоченные части логического ключа и их соответствие полям. Поддерживаемые операции ограничены явным набором; произвольные C#-лямбды не транслируются. |
| `DbfSession.Open(root)` | Создаёт область владения ресурсами и фиксирует абсолютный базовый каталог относительных путей DBF. Не создаёт DBF, не меняет рабочий каталог процесса и не означает отдельную VM. |
| `OpenTable(path, mapping, ...)` | Разрешает путь DBF по правилам раздела 5.1, открывает существующий файл, читает схему, проверяет mapping, подключает все объявленные индексные файлы относительно каталога этого DBF и проверяет теги до возврата таблицы. Абсолютные пути CDX используются напрямую. При ошибке освобождает уже полученные ресурсы. |
| `cities.Index(descriptor)` | Возвращает типизированный доступ к объявленному тегу. Проверяет принадлежность descriptor mapping этой таблицы. Не оставляет публичного активного индекса и не открывает CDX лениво. |
| `Dispose()` | Идемпотентно завершает владение соответствующими ресурсами. Сеанс пытается закрыть все свои таблицы и курсоры даже при ошибке освобождения одного из них. Политика представления нескольких ошибок уточняется. |

Предлагаемый режим по умолчанию — `SharedReadOnly`; запись включается явно. Набор режимов: `SharedReadOnly`, `SharedReadWrite`, `ExclusiveReadOnly`, `ExclusiveReadWrite`. Read-only должен обеспечиваться Harbour RDD, а не только проверкой в C#.

Правила разрешения путей закреплены в разделе 5.1 и не относятся к открытым вопросам. Окончательная форма параметров и options-объекта ещё обсуждается.

Все файлы из mapping подключаются до записи; один и тот же файл с несколькими объявленными тегами подключается один раз. Нужен способ объявить сопровождаемый индексный файл без типизированного поискового свойства; кандидат — `IndexBag("other.cdx")`. Его точное имя и поведение пока не закреплены.

Автоматического создания, восстановления или перестроения индексов при несовпадении нет. Проверка выражения не должна сводиться к предположению, что имя тега совпадает с именем поля. Политика сравнения эквивалентных Harbour-выражений и неподдерживаемых тегов остаётся открытой.

### 5.1. Правила разрешения путей DBF и CDX

1. `DbfSession.Open(root)` принимает полный абсолютный путь к базовому каталогу. Корень фиксируется на время жизни сеанса. Сеанс не вызывает `Directory.SetCurrentDirectory` и не полагается на последующие изменения рабочего каталога процесса.
2. Относительный путь DBF в `OpenTable` разрешается относительно корня сеанса, включая вложенные каталоги. Например, `catalog\customers.dbf` и `sales\orders.dbf` обозначают две разные таблицы под одним корнем.
3. Полный абсолютный путь DBF используется напрямую; корень сеанса к нему не добавляется. Таблица может находиться вне корня сеанса: корень задаёт базу относительных путей, а не ограничение доступа к каталогам.
4. Относительный путь CDX в `Index(..., file: ...)`, `CompositeIndex(..., file: ...)` или объявлении сопровождаемого индексного файла разрешается относительно каталога фактически открываемого DBF. Это правило одинаково для DBF, открытого относительным и абсолютным путём.
5. Полный абсолютный путь CDX используется напрямую. Он может указывать на другой каталог, если такое расположение поддерживается конкретным набором данных и RDD.
6. `.` и `..` разрешаются относительно соответствующей базы, после чего путь нормализуется. Для Windows принимаются обычные полные пути с диском и полные UNC-пути. Неоднозначные пути вида `D:customers.dbf` или `\catalog\customers.dbf` отклоняются: они зависят от текущего диска или каталога процесса.
7. Если разрешённый файл отсутствует или недоступен, открытие завершается ошибкой с указанием разрешённого пути. Поиск по другим каталогам, подстановка другого файла и автоматическое создание не выполняются. Правило отсутствующего CDX одинаково для чтения и записи: объявленный файл обязателен.

Для условного корня `D:\SampleData` примеры разрешения выглядят так. Имена CDX также иллюстративные.

| Вход | База | Разрешённый путь |
| --- | --- | --- |
| DBF: `catalog\customers.dbf` | Корень сеанса | `D:\SampleData\catalog\customers.dbf` |
| DBF: `sales\orders.dbf` | Корень сеанса | `D:\SampleData\sales\orders.dbf` |
| CDX: `customers.cdx` для первого DBF | Каталог первого DBF | `D:\SampleData\catalog\customers.cdx` |
| CDX: `orders.cdx` для второго DBF | Каталог второго DBF | `D:\SampleData\sales\orders.cdx` |
| CDX: `indexes\customers.cdx` для первого DBF | Каталог первого DBF | `D:\SampleData\catalog\indexes\customers.cdx` |
| DBF: `D:\Archive\customers.dbf` | Уже абсолютный путь | `D:\Archive\customers.dbf` |
| CDX: `customers.cdx` для DBF из архива | Каталог DBF в архиве | `D:\Archive\customers.cdx` |
| CDX: `D:\SharedIndexes\customers.cdx` | Уже абсолютный путь | `D:\SharedIndexes\customers.cdx` |

Mapping хранит описание исходных путей без привязки к сеансу. Разрешённые абсолютные пути и открытые ресурсы принадлежат экземпляру таблицы. Один mapping можно использовать для одинаковой схемы в разных каталогах: относительный `file: "table.cdx"` каждый раз разрешается рядом с соответствующим DBF, а не рядом с предыдущей открытой таблицей.

Одинаковые имена DBF или CDX в разных каталогах не должны конфликтовать из-за имени файла или автоматически созданного алиаса. Нормализация путей не обещает распознавание всех вариантов физической идентичности файла через ссылки файловой системы; политика повторного открытия одного файла отдельно обсуждается при выборе модели ресурсов.

## 6. Контракты чтения и поиска

| Операция | Результат и семантика |
| --- | --- |
| `ReadAt(recordNumber)` | `DbfRecord<T>` или `null`, если физическая запись отсутствует либо скрыта выбранной политикой удаления. Нумерация с 1; 0 и отрицательные значения — ошибка аргумента. |
| `Read(reference)` | Новое чтение той же физической позиции; проверяет владение и время жизни ссылки. Не обещает неизменность содержимого с прошлого чтения. |
| `FindFirst(key)` | Первая видимая запись с равным индексным ключом либо `null`. Не предполагает уникальности. |
| `FindLast(key)` | Последняя видимая запись с равным индексным ключом либо `null`. |
| `EqualTo(key)` | Ленивое перечисление видимых записей с равным ключом в порядке индекса. Отсутствие совпадений даёт пустую последовательность. |
| `Range(from, to, bounds)` | Ленивый обход между полными преобразованными ключами. Включение границ задаётся явно. Сравнение следует правилам RDD и тега. |
| `cities.Scan()` | Ленивый полный обход в физическом порядке, с выбранной политикой удаления. |
| `index.Scan()` | Ленивый обход в порядке тега. Не обещает охват физических записей, отсутствующих в индексе из-за его особенностей. |
| `Prefix(selector, value)` | Фиксирует полное значение очередной ведущей части составного ключа. Повторный `Prefix` разрешён только для следующей части. |
| `StartingWith(selector, text)` | Ограничивает следующую текстовую часть её началом. Требует известной структуры и поддерживаемого преобразования; не дополняет префикс до полного ключа. |

Отсутствие записи отличается от ошибки доступа, преобразования или повреждённого индекса: такие ошибки не превращаются в `null` или пустой результат.

Предлагаемый тип физического номера в публичном API — `long`, но принимаемый диапазон определяется реально поддерживаемыми операциями. До расширения и проверки текущих счётчиков и блокировок `int` нельзя обещать полноценную работу с номерами выше `Int32.MaxValue`. Выбор окончательного диапазона входит в открытые вопросы.

Политика помеченных записей задаётся при открытии таблицы и одинакова для чтения, поиска и обхода. Предлагаемое значение по умолчанию — исключать помеченные записи; режим включения позволяет увидеть `IsDeleted`. `Recall(reference)` должен уметь адресовать скрытую помеченную запись независимо от фильтра чтения. Точное имя настройки ещё не выбрано.

Каждый результат содержит отдельный материализованный `Value`. Его можно читать после закрытия сеанса. `Reference` в нём после закрытия непригодна для новых операций.

Перечисление требует открытой таблицы. `foreach`/`Dispose` перечислителя освобождает курсор; сеанс закрывает оставшиеся курсоры при завершении. Повторное перечисление выполняет новое чтение. Нельзя удерживать глобальную блокировку VM между пользовательскими шагами `foreach`.

Вложенный поиск или обход не должен сдвигать внешний обход. Целевой контракт — независимый внутренний курсор каждого перечисления; способ его обеспечения пока не выбран. Совместное чтение не является согласованным снимком всей таблицы; добавления и изменения другими процессами требуют определённой и проверенной политики видимости.

`Where`, `Select`, `OrderBy` после перечисления — обычный LINQ to Objects. Они не используют CDX автоматически и не сокращают список читаемых полей. Оптимизированная проекция, подсчёт, пагинация и ограниченный перевод предикатов проектируются отдельно при необходимости.

## 7. Правила составных ключей и выражений

### 7.1. Декларативное описание

Для поддерживаемого набора частей mapping служит одним описанием выражения на полях и преобразования поисковых значений. `HarbourExpression` может предоставлять диагностическое представление:

```csharp
mapping.ByViewAndName.HarbourExpression
// STR(KVIEW, 4, 0) + UPPER(PADR(CITY, 30))
```

Эта возможность не означает, что библиотека автоматически создаёт индекс или умеет доказать эквивалентность произвольных выражений существующего тега.

В первом наборе кандидатов: `Str(width, decimals)`, `PadRight(width)`, `AllTrim()`, `Upper()`, `Dtos()`. Точный набор и ограничения должны опираться на независимые проверки Harbour, включая наличие нужных функций в собранной DLL.

Ключевые правила:

- Кодировка, регистр, дополнение и сравнение следуют Harbour/RDD. Нельзя незаметно использовать .NET culture, `ToUpperInvariant` или UTF-16 длину как замену правилам индекса.
- `TrimEnd` модели не является преобразованием ключа. Обычный тег по строковому полю тоже требует согласования длины и представления поискового значения с самим полем и настройками RDD.
- Разные логические значения могут получить один ключ после `Upper`, усечения или форматирования. Типизация не создаёт уникальность и обратимость.
- Для `Str` нужно проверять ширину, знак и дробную часть. Лексикографический порядок полученного ключа не всегда совпадает с числовым порядком исходного значения.
- `Dtos` формирует ключ даты без времени. Допустимость ненулевого времени, пустой даты и `DateTime.Kind` должна быть явно задана.
- Непредставимый символ, числовое переполнение и лишняя точность дают ошибку до обращения к индексу. По умолчанию поисковые значения не должны молча теряться или усекаться; допустимые потери задаются явно. Взаимодействие этого правила с усечением внутри `PADR` ещё нужно закрепить.
- Полный ключ и текстовый префикс формируются по разным правилам. Нельзя искать начало слова через полный ключ с дополняющими пробелами или строить верхнюю границу добавлением произвольного максимального Unicode-символа.

Пример диапазона от `CityNameKey(1, "А")` до `CityNameKey(1, "М")` ограничивает полные ключи. Он не означает включение всех названий, начинающихся с «М».

Запрос по неведущей части должен завершаться ошибкой до перечисления, а не переходить к полному обходу:

```csharp
byViewAndName.Prefix(k => k.Name, "Кострома");
// Ошибка: сначала требуется значение ViewId.
```

`Prefix` и `StartingWith` доступны только там, где доказуемо корректны для структуры и преобразований тега. Нельзя обещать их для всех сортировок, преобразований, убывающих тегов или индексов `FOR`/`UNIQUE` без проверки.

### 7.2. Произвольный Harbour-блок

Для старого выражения, которое не помещается в набор `DbfKeyFormat`, нужен явный выход к Harbour. Пример тега: `IIF(KVIEW = 1, 'A', 'B') + UPPER(PADR(CITY, 30))`.

```csharp
// Свойство CityMapping:
public DbfIndexMapping<City, CityNameKey> ByCategoryAndName { get; }

// Фрагмент его конструктора:
ByCategoryAndName = Index<CityNameKey>(
        file: "city_category.cdx",
        tag: "BY_CATEGORY_NAME")
    .SearchKey(
        harbour:
            "{|view, name| " +
            "IIF(view = 1, 'A', 'B') + UPPER(PADR(name, 30)) }",
        arguments: k => new object[] { k.ViewId, k.Name });

// Прикладной код:
var byCategory = cities.Index(mapping.ByCategoryAndName);
var record = byCategory.FindFirst(new CityNameKey(1, "Кострома"));
```

Это дополнительный пример, не часть цельного mapping выше. При его добавлении `city_category.cdx` также открывается при открытии таблицы. Блок задан разработчиком в mapping, значения передаются аргументами без интерполяции в Harbour-код.

Начальный контракт такого описания — поиск полного ключа. Диапазоны допустимы только после явной проверки типа результата и порядка. Структуру префиксов библиотека по блоку не угадывает; её описание или отказ от таких операций — отдельное решение. Соответствие произвольного блока выражению тега лежит на конфигурации и проверках.

## 8. Контракты изменения

| Операция | Предлагаемый результат и поведение |
| --- | --- |
| `Insert(value)` | Добавляет запись, фиксирует её по принятому правилу, читает результат с генерируемыми значениями и возвращает `DbfRecord<T>`. Не изменяет переданный объект и не выполняет upsert. |
| `Update(reference, Action<T>)` | Возвращает новый `DbfRecord<T>` после успешного изменения; callback работает с отдельным свежим объектом под блокировкой. |
| `MarkDeleted(reference)` | Помечает запись удалённой под блокировкой и фиксирует изменение. Физическая запись сохраняется. |
| `Recall(reference)` | Снимает пометку удаления под блокировкой и фиксирует изменение. Не зависит от видимости удалённых при обычном чтении. |

Последовательность `Update`:

1. Проверить время жизни таблицы, режим записи и принадлежность ссылки.
2. Получить блокировку конкретной записи. При неудаче callback не вызывать.
3. Перечитать актуальные данные после получения блокировки.
4. Создать временную модель и выполнить callback один раз.
5. Определить изменённые записываемые поля и проверить все значения до первой native-записи.
6. Записать изменённые поля, выполнить предусмотренный Harbour `Commit`, перечитать итоговые данные с учётом служебных полей.
7. Освободить блокировку в любом исходе; при успехе вернуть новый результат.

Изменение не должно переписывать поля вне mapping, генерируемые поля или нормализованные при чтении поля, которые пользователь не менял. Если итоговые значения не изменились, предлагается не выполнять запись и не продвигать служебную версию без необходимости; проверка этого поведения обязательна.

При исключении callback или ошибке предварительной валидации native-запись изменений не начинается. После начала native-записи ошибка может оставить частичный результат. Ошибка фиксации или освобождения блокировки должна сохранять контекст основной ошибки; автоматический повтор операции не выполняется. Точная модель составных ошибок и состояние таблицы после такого сбоя — открытые вопросы.

`Commit` означает предусмотренную фиксацию через Harbour RDD. Он не добавляет rollback и не обещает согласованную транзакцию между DBF, FPT и CDX или отдельную гарантию устойчивости к потере питания.

Для `Insert` доступные значения проверяются до `Append`. Поддержка блокировок добавления, пропущенных полей, незаписанных полей модели и служебных значений требует отдельного контракта. После успешного `Append` последующий сбой может оставить добавленную или частично заполненную запись; автоматического удаления или отката не обещаем.

Callback не сохраняется библиотекой и не повторяется автоматически. Сохранённый пользователем объект callback не становится отслеживаемой сущностью. Асинхронные callback и повторный вход в операции этой библиотеки из callback в первую версию не включаются.

Ранее найденный результат может устареть до `Update`. Повторное чтение под блокировкой защищает вычисление нового значения, но не проверяет ожидания, основанные на старом результате. Оптимистическая проверка версии, например по `^`, проектируется отдельным явным режимом.

Неудачная блокировка должна иметь отдельную категорию ошибки. Предлагаемое исходное поведение — одна попытка без скрытых повторов; timeout и политика повторов требуют отдельного решения. Бизнес-ключ `City.Code` не считается уникальным автоматически; поиск с последующим `Insert` не превращается в атомарный upsert.

## 9. Типы, служебные поля и ошибки

Типизированный API должен преобразовывать по схеме, а не только через `Convert.ChangeType`:

| Область | Целевой контракт и оставшиеся ограничения |
| --- | --- |
| `C`, `M` | `string`; проверка представимости символов при записи. Для `C` длина проверяется в выбранном представлении DBF. FPT обслуживает Harbour; DBT не объявляется подтверждённым. |
| `N` | Проверяемое преобразование в выбранный тип свойства, без тихого переполнения или округления. Точный `decimal` требует отдельной проверки транспорта: текущий JSON-путь может вернуть `Double`. |
| `L` | `bool`; нестандартные или пустые представления требуют отдельного решения по схеме. |
| `D` | Кандидат: `DateTime?`, где пустая дата соответствует `null`. Время и `Kind` требуют явной политики; не наследовать молчаливое отбрасывание времени случайно. |
| `@`, `T` | Кандидат: `DateTime?` с точностью до миллисекунды; без автоматического преобразования часового пояса. `T` не считается независимо проверенным только из-за обработки в Beta. |
| `+`, `=`, `^` | Значения формирует Harbour; по умолчанию доступны для чтения и исключены из пользовательской записи. Синтаксис объявления генерируемых свойств и работа со значениями CLR по умолчанию ещё выбираются. |

Кодировка из `Encoding.GetEncoding(866)` в примере описывает нужную кодовую страницу. Сам по себе стандартный encoder может заменять символы, поэтому новый контракт требует строгой проверки или error fallback, а не предположения о строгости переданного объекта.

Ошибки нужно различать по категориям: mapping/схема/индекс, аргумент или ссылка от другой таблицы, закрытый ресурс, преобразование значения, блокировка, Harbour/RDD и сбой освобождения. Точные имена исключений пока не закреплены. Сообщение должно содержать операцию, таблицу и при необходимости поле, тег и номер записи, сохраняя исходную причину.

`Save(model)` и скрытый change tracking в первую версию не входят: адрес записи и ожидания по конкурентным изменениям должны быть явными.

## 10. VM, потоки и совместимость с текущим API

Сеанс является владельцем ресурсов, но не доказывает изоляцию настроек Harbour. Операция высокого уровня должна выбирать нужную область и выполнять зависимую последовательность без вмешательства другой операции. Переключение алиаса и отдельная блокировка вокруг каждого P/Invoke этого не обеспечивают.

Модель исполнения требуется выбрать до реализации: общий поток-владелец native runtime либо единый внутренний исполнитель с необходимой диспетчеризацией. Один `lock` не является доказательством допустимости вызова VM из другого потока. Обещаний свободной многопоточности и `async` в первой версии нет.

Настройки `SET DELETED`, автоматическое открытие CDX, сортировка и другие общие параметры не должны зависеть от случайного последнего вызова. Нужно определить, что сохраняется и восстанавливается вокруг операций и какие внешние вызовы во время работы сеанса запрещены.

Низкоуровневый `DbfHarbour` и экспериментальный `Beta.Database` сохраняются. Прямое изменение их текущей области, настроек и блокировок во время высокоуровневой операции не обещается безопасным. Режим смешанного использования и доступ к диагностическому алиасу обсуждаются отдельно.

## 11. Открытые вопросы

| Вопрос | Предлагаемое направление / что решить |
| --- | --- |
| Полнота индексного набора | Mapping перечисляет все известные файлы, включая файлы без публичного поискового descriptor. Как подтверждать полноту и диагностировать неполное описание? |
| Проверка выражений | Какие метаданные сверять обязательно? Как сравнивать эквивалентные записи выражений? По умолчанию отклонять неподдерживаемую семантику, не переходить к сканированию. |
| Формат частей ключа | Зафиксировать порядок преобразований, длину в нужной кодировке, ограничения знака/точности и явное усечение. |
| Префиксы и диапазоны | Какие сочетания преобразований и сортировок поддерживаются? Как учитывать убывающие теги, `FOR` и `UNIQUE`? |
| Произвольные выражения | Оставить `SearchKey` расширением или включить в первую версию? Какие функции гарантированно связаны с DLL и допустимы в блоке? |
| Генерируемые поля | Выбрать `.Generated()`/иной синтаксис; отвергать явную запись или исключать значение из записи. |
| Неполная модель при Insert | Какие поля обязательны? Какие DBF-значения по умолчанию допустимы? Нужен ли отдельный тип/объект для частичного добавления? |
| Материализация | Нужны ли immutable-модели, конструкторы и пользовательские конвертеры сразу или сначала только классы с доступными свойствами? |
| Конкурентные изменения | Добавлять ли явную проверку исходного `^`/полей? Как сообщать конфликт без обещания общей транзакции? |

| Удаление | Подтвердить исключение помеченных по умолчанию, имя настройки, поведение Update для скрытой записи и идемпотентность MarkDeleted/Recall. |
| Номера и ссылки | Уточнить максимальный номер, поведение при замене файла и внешнем PACK. Где неизменность структуры должна быть обязательным условием? |
| Курсоры | Независимые области или другой механизм сохранения состояния? Определить видимость изменений и ресурсную стоимость вложенных обходов. |
| Потоки и VM | Выбрать единую модель исполнения для всех сеансов, правила сохранения глобальных настроек и смешанного доступа. |
| Сбои записи/Dispose | Как представлять несколько ошибок и запрещать дальнейшую работу с состоянием, корректность которого неизвестна? |
| Публичный синтаксис | Подтвердить названия, режимы, передачу настроек параметрами либо options-объектом и типы ключей. Базы разрешения путей DBF/CDX закреплены в разделе 5.1; политика повторного открытия одного файла ещё обсуждается. |

## 13. Проверки будущей реализации

Этот список фиксирует критерии, а не сообщает о выполненных проверках нового API.

- Сохранить действующие лёгкие примеры x86: основные поля, FPT, даты, timestamp, служебные значения, read-only и два отдельных CDX. Типизированный слой не должен расширять заявленную поддержку без новых свидетельств.
- Добавить специальные синтетические сценарии для City: многотеговый CDX и отдельные файлы, повторы ключей, преобразования регистра, фиксированные части, ведущие префиксы, границы диапазонов и неподдерживаемые теги.
- Проверять результат записи независимым Harbour после повторного открытия без перестроения индексов. Открывать все сопровождаемые индексы, даже если прикладной код не получает их через `Index`.
- Проверять крайние значения длины и чисел, непредставимые символы, начальные/конечные пробелы, пустые даты, точность timestamp и отсутствие неоговорённых потерь `decimal`.
- Проверять принадлежность и время жизни ссылок, ранний выход из `foreach`, исключения во время перечисления, вложенные поиски и закрытие сеанса с активным перечислителем.
- Проверять открытие таблиц из `catalog` и `sales` в одном сеансе, относительные и абсолютные пути DBF/CDX, вложенные каталоги индексов и переиспользование mapping между каталогами. Изменение рабочего каталога процесса не должно менять разрешение путей. Отсутствующие файлы не подменяются поиском в другом каталоге; одинаковые имена в разных каталогах не смешиваются.
- Проверять неудачную блокировку, однократный callback, no-op, исключение до записи, частичный сбой после начала записи и сохранение обеих причин при ошибке освобождения.
- Проверять сопровождение служебных полей и отсутствие лишней записи пустой добавленной строки до заполнения. Текущий `PositionForAccess` специально учитывает, что переход к dirty-записи может сбросить её и продвинуть версию.
- Конкурентную запись проверять отдельными процессами, а потоковую модель — отдельно от файловых блокировок. Сериализация доступа к VM и блокировка DBF решают разные задачи.
- Любую запись выполнять на временных синтетических копиях с контролем сохранности исходников. CRM, SMB и x64 остаются отдельными этапами, как указано в текущей документации.

## 14. Готовность проекта API к реализации

Проект можно считать готовым к следующему этапу, когда цельный пример не содержит неоговорённых обещаний, для каждого метода определены результат, отсутствие записи, ошибка, время жизни и влияние на файлы, а блокирующие вопросы по индексам, VM, блокировкам и преобразованию значений разрешены либо явно исключены из первой версии.

При подготовке плана исполняемый код, тесты и данные не изменялись. Текущее состояние реализации описано в руководстве по типизированному API.
